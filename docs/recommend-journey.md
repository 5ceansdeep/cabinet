# 추천 정확도를 올려 온 기록 (9/26 ~ 10/2)

"지금 기분을 적으면 맞는 곡을 건져 준다"는 한 줄짜리 기능이 어떻게 지금 모양이 됐는지 적어 둔다.
무엇을 바꿨는지보다 **왜 바꿨는지, 그리고 숫자가 어떻게 움직였는지**를 중심으로.

> 숫자 읽는 법 — 평가 세트(`backend/src/recommend/eval.json`)의 요청마다 "상위 5곡 안에 들어야 할 곡"을 사람이 정해 두고,
> 실제 상위 5곡에 몇 개 들었는지(재현율)를 잰다. 세트는 30개(Claude 초안) → 39개(사용자 확정) → 45개로 바뀌었고 곡 풀도 88 → 305곡으로
> 늘었기 때문에, **서로 다른 시기의 숫자는 그대로 비교하지 않는다.** 같은 표 안의 숫자만 비교한다.

---

## 0. 지금 모양 한 장 요약

```
요청문 ──▶ [해석] Gemini 가 "이런 곡이면 좋겠다"를 곡 설명과 같은 틀로 풀어 씀
             + 제목에 나올 낱말(words) + 애매하면 두 번째 읽기(alt) + 목표 에너지·밝기
        ──▶ [1단계] 곡 305개와 비교
             점수 = 0.5 × 뜻(임베딩 코사인, 곡 풀 평균을 뺀 뒤) + 0.5 × 소리(에너지·밝기 거리)
                  + 글자 일치 가산 − 자주 던져진 곡 감점
             가수당 2곡까지 먼저, 말한 가수는 맨 앞, 말한 장르는 거름 → 후보 20곡
        ──▶ [2단계] Gemini 가 후보 20곡의 곡 설명을 읽고 순서를 다시 매김(+ 신의 한마디)
             6초 넘으면 1단계 순서 그대로
        ──▶ 10곡
```

곡 쪽은 미리 만들어 둔다: 가사(LRCLIB) + 소리 숫자(ReccoBeats) → Gemini 가 쓴 곡 설명 → 임베딩. 새벽 배치가 새 곡을 채운다.

## 1. 낱말 사전 + 태그 코사인 (9/26 ~ 9/28) — 출발점

처음엔 요청문을 **한국어 낱말 사전**으로 Last.fm 태그에 대응시키고, 곡의 Last.fm 태그와 코사인을 쟀다(DRIFT 에서 옮긴 방식).

금방 한계가 보였다.
- **한국 곡은 Last.fm 에 분위기 태그가 거의 없다.** 분위기 일치도가 대부분 0% 라 근거 없는 숫자였고, 결국 뺐다(9/28).
- 태그가 없는 곡은 iTunes 장르로 메웠지만, 미국 스토어는 한국 곡을 거의 다 "K-Pop" 하나로 묶어 발라드·인디 구분이 안 됐다.
- 사전에 없는 말은 전부 같은 기본 태그로 떨어졌다. **"안녕하세요"와 "집에 가고 싶어요"가 같은 곡을 냈다.**

교훈: 태그는 곡을 구별하기엔 너무 성기다. 곡마다 "무슨 곡인지"를 문장으로 가져야 한다.

## 2. 곡 설명 + 임베딩 + 소리 숫자 (9/30) — 구조를 갈아엎다

설계 문서(`docs/recommend-plan.md`)를 다시 쓰고 두 축으로 나눴다.

- **뜻**: Gemini 가 곡마다 가사·제목·소리를 읽고 `감정 / 상황 / 가사 / 소리` 틀로 설명을 쓴다 → 임베딩(768차원).
- **소리**: ReccoBeats 가 30초 미리듣기를 분석한 에너지·밝기 숫자.

요청문도 **바로 임베딩하지 않고, 곡 설명과 똑같은 틀로 풀어 쓴 뒤** 임베딩한다. 같은 말투끼리 비교해야 잘 맞는다는 판단이었다
("새벽에 혼자 걷는 기분"과 "감정: … 상황: …"을 바로 비교하면 형식 차이가 점수를 먹는다).

시험: "춤추고 싶어" → 키키·르세라핌·Hype Boy, "못 잊겠어" → The Day·잔나비. 사전 방식에선 불가능하던 결과.

## 3. 평가 세트를 만들고 "허브"를 잡다 (9/30)

감으로 고치다간 한쪽을 고치면 다른 쪽이 망가지는 걸 모른다. 그래서 **평가부터** 만들었다.
- `eval.json` + `npm run eval`: 뜻 비중 A 를 바꿔 가며 재현율을 표로.
- 해석·재정렬 결과는 `.eval-cache.json`·`.eval-rerank.json` 에 캐시하고 git 에 올린다 — 같은 해석으로 몇 번이고 다시 재도 Gemini 를 안 쓴다.

평가를 돌리자마자 문제가 드러났다. **어느 요청에나 같은 곡(나의 X에게·Everything·너의 모든 순간)이 끼었다.**
곡 설명이 다들 "밤·혼자·아련함" 쪽이라, 곡 풀 평균에 가까운 곡이 모든 요청과 가깝게 잡히는 것 — 임베딩 검색에서 흔한 **허브(hubness)** 문제다.

해결: **곡 풀 평균 벡터를 요청·곡 양쪽에서 빼고 다시 정규화한 뒤** 코사인. 공통 성분(다들 비슷한 "밤 감성")이 사라지고 곡마다 다른 부분만 남는다.

| (Claude 초안 30개) | 하나라도 맞음 | 재현율 |
|---|---|---|
| 처음 | 24/30 | 43% |
| 평균 빼기 + A 0.5 | **29/30** | **68%** |
| 뜻만(A 1.0) | — | 61% |

소리 숫자를 섞는 게 뜻만 쓰는 것보다 낫다는 것도 이때 확인했다.

## 4. 작지만 컸던 순위 버그 (9/30)

"한 가수로 몰리지 않게 가수당 1곡 먼저"라는 규칙이, 가수마다 첫 곡을 다 줄 세운 뒤에야 둘째 곡을 보여 줬다.
그래서 합산 점수 2~3등감인 트와이스 FANCY 가 **111등**이었다. 가수당 2곡까지로 바꿨다.

같이 시험한 "공감형 풀어 쓰기"(위로 대신 같은 감정으로)는 28/39·37% 로 **나빠져서 되돌렸다**. 위로를 원하는 요청이 틀렸다.
→ 요청 하나에 한 규칙을 덮어씌우면 안 되고, 요청 종류를 나눠야 한다는 힌트가 됐다(6장).

## 5. 2단계 재정렬 (9/30 ~ 10/1)

1단계는 벡터 거리라 "대충 이 동네" 까지는 잘 찾지만, 미묘한 차이(후련한 이별 vs 슬픈 이별)는 놓친다.
그래서 **1단계 후보 20곡의 곡 설명을 Gemini 가 직접 읽고 순서를 다시 매기게** 했다(LLM 재정렬). 신의 한마디도 같은 호출로 받는다.

처음엔 재정렬 순서를 **버렸다**. 9/30 엔 1단계가 더 나았기 때문이다 — 그땐 곡 설명이 "가사 없는 연주곡" 투성이라 재정렬이 읽을 게 없었다(6장).
곡 설명을 고친 10/1 에 다시 재 보니 재정렬이 확실히 이겼고, 그 순서를 화면에 쓰기 시작했다.

- 말한 가수 곡은 재정렬이 섞지 않게 맨 앞에 고정(`finalOrder`).
- 6초 넘으면 1단계 순서로 — 화면이 멈추면 안 된다.
- 곡별 이유 문장은 화면에서 안 쓰길래 프롬프트에서 뺐다 → 응답 5.3초 → 4초.

## 6. 곡 설명의 질을 고치다 (10/1) — 가장 오래 걸린 부분

재정렬이 아무리 똑똑해도 **곡 설명이 엉터리면** 소용이 없다. 여기서 세 번 시행착오가 있었다.

**(1) 노래인데 "가사 없는 연주곡"이라고 쓴 92곡.**
곡 풀 244곡 중 92곡이 가사 없이 설명됐는데, 밤편지·Gee 같은 노래가 대부분이었다.
- LRCLIB 은 한국 곡을 영문 이름(IU - Through the Night)으로 갖고 있어 한글로 찾으면 0건
- 굽은 따옴표(Linus’ Blanket)가 다른 글자로 잡힘, 망 실패도 "가사 없음"으로 기록

가사를 못 받으니 Gemini 가 "가사 없는 연주곡"이라 썼고, **그 두루뭉술한 설명이 차분한 요청마다 끼어들었다.**
→ 미국 스토어 표기로 한 번 더 찾기, LRCLIB 기록으로 `가사 / 연주곡 / 못 찾음` 셋으로 나누기. 가사를 찾은 곡 152 → 259곡.

**(2) 구체 서사형 — 실패.**
설명이 다들 비슷하니 "이 곡만의 장면"을 구체적으로 쓰게 했다(밤양갱 → "진수성찬 대신 달디단 밤양갱 하나면 충분했다는 비유").
글은 좋아졌는데 **곡 벡터가 감정 쪽에서 소재·행동 쪽으로 끌려가** 감정 요청 재현율이 42% → 28% 로 떨어졌다.
가사 없는 재즈는 생활 장면을 지어내 "배고파"에 줄줄이 끼어들었다.

**(3) [핵심어 3개] + 묘사 — 정착.**
칸마다 검색에 쓰는 흔한 핵심어 3개를 대괄호로 먼저 박고, 이어서 이 곡만의 묘사를 쓴다.
```
감정: [이별, 씁쓸함, 담담함] 거창한 사랑 대신 달디단 밤양갱 하나면 충분했다는 …
```
핵심어가 감정 요청을 붙잡고(앵커), 묘사가 소재 요청을 붙잡는다. 가사를 모르는 곡은 상황 칸을 듣는 환경(공부·휴식·드라이브)으로만 제한해 지어내지 못하게 했다.
요청 풀어 쓰기도 같은 형식으로 바꿨다.

| (기존 39개) | 곡 설명 | 순서 | 곡 풀 | 재현율 |
|---|---|---|---|---|
| | 옛(가사 없는 곡 많음) | 1단계 | 243 | 42% |
| | 구체 서사형 | 1단계 | 304 | 23% |
| | [핵심어]+묘사 | 1단계 | 304 | 27% |
| | **[핵심어]+묘사** | **재정렬** | 304 | **38%** (45개 전체 41%) |

1단계만 보면 옛 방식보다 낮지만, 곡이 60곡 늘어 경쟁이 세졌고 재정렬과 합치면 제일 높다.
(교훈 하나 더: 이 단계에서 305곡을 **표본 없이 두 번 통째로 다시 써서** 시간과 Gemini 호출을 버렸다. 이후 "DB 전체 다시 쓰기는 표본으로 먼저 잰다"가 규칙이 됐다.)

## 7. 요청 종류별로 읽기 (10/1)

"배고파"를 기분만 짐작하라고 시켜 놨더니 소재(배고픔)가 사라지고 두루뭉술한 위로곡이 나왔다. 해석 프롬프트를 요청 종류별로 나눴다.
- 소재·몸 상태(배고파, 비 온다) → 그 소재를 노래하는 곡. 가사 칸에 낱말 그대로 → 기리보이 "배고파" 1위
- 감정(슬퍼) → 같은 감정에 머무는 곡. 슬픈 사람에게 응원가를 주지 않는다
- 지침(번아웃) → 조용한 위로 / 할 일·장소(드라이브) → 어울리는 분위기
- 가수·장르를 직접 말하면 그대로 거름("오아시스의 신나는 노래" → 오아시스 곡 먼저, 그 안에서 소리 점수)

## 8. 사람들의 손으로 보정 (10/1 ~)

- **던진 곡 기록**: 여러 사람이 자꾸 던지는 곡은 1단계 점수를 조금 깎는다(던질 때마다 0.01, 최대 0.05, 30일). 한 곳에서 같은 곡은 하루 한 번만 센다.
- **"다시 찾기"** 는 던진 곡들 쪽에서 요청 벡터를 밀어낸다 — 비슷한 곡이 덜 나온다.
- **행동 기록**(10/2): 재생·끝까지 들음에 그 곡을 꺼낸 요청문을 같이 남긴다. 쌓이면 "이 편지엔 이 곡이 끝까지 들렸다"로 사람이 만든 45개 대신 **진짜 평가 세트**를 만든다.

## 9. 엉뚱하고 짧은 요청 (10/2) — 지금

"미쳤어"를 넣었더니 한숨·도망가자·Relieved 같은 잔잔한 위로곡만 나왔다. 해석이 "지쳐서 미침" 하나로 읽고 7장의 지침 규칙을 탔기 때문이다.
곡 풀에 송지은 "Crazy"·키키 "Pop Off"가 있었는데 1단계 후보 20곡에 못 들어 재정렬도 살릴 수 없었다. 곡 풀을 늘리지 않고 두 가지를 더했다.

**글자 일치 가산(하이브리드 검색).** 해석이 `words` — 곡 제목·가사에 그대로 나올 낱말을 한·영으로 — 를 같이 낸다(미쳤어 → 미쳐·crazy).
제목에 있으면 +0.1, 곡 설명 [핵심어]에 있으면 +0.04. 벡터 검색이 놓치는 "글자 그대로"를 보완하는, 검색에서 흔한 dense + lexical 조합이다.

**두 갈래 읽기.** 짧고 여러 뜻으로 읽히는 요청이면 두 번째 읽기(`alt`)를 같은 호출로 받고 임베딩만 하나 더 한다.
두 읽기의 순위에서 번갈아 후보를 뽑고, 재정렬 뒤에도 번갈아 10곡을 세운다. 사용자는 맞는 쪽만 남기고 던지면 된다 — 결과가 한쪽으로 몰리는 것보다 낫다.

| (45개) | 1단계 | 재정렬 후 |
|---|---|---|
| 전 | 31% | 41% |
| 새 해석, 가산 없음 | 30% | — |
| **새 해석 + 가산** | **36%** | 41% |

평가 세트는 대부분 긴 문장이라 두 갈래는 1개만 걸렸고 최종 숫자는 그대로다. 대신 짧은 요청이 눈에 띄게 달라졌다.
- 미쳤어 → 해석 "신남·황홀함·흥분 / 분노·어이없음" → Pop Off Pop Off, BREAK MY SOUL, Gangnam Style, **Crazy** …
- 종달새 → **Blue Bird**(이키모노가카리), Happy Things, … **Bird Calls**(밍거스)

## 10. 쓰임 장면 — 요청 쪽에만 (10/2)

사용자 제안: 곡이 실제로 쓰이는 곳(드라마 OST·예능 브금·밈·챌린지)을 설명에 넣으면 "의심돼 → 추리 브금" 같은 고리가 생긴다.
표본(평가에 걸린 99곡)만 메모리에서 새 설명으로 바꿔 끼워 DB 는 건드리지 않고 쟀다.

| (45개) | 1단계 | 재정렬 후 |
|---|---|---|
| 지금 | 35% | 41% |
| **요청에만 쓰임 장면** | 37% | **46%** |
| 요청 + 곡 설명 둘 다 | 32% | 39% |

곡 쪽은 Gemini 가 아는 39곡에만 칸이 생겼고, 대부분 "숏폼 챌린지·예능 브금" 같은 일반론이라 그 곡들끼리 비슷해져(허브) 다른 요청에 끼어들었다. 일부는 사실도 의심스러웠다.
그래서 곡 설명 305곡 다시 쓰기는 하지 않고, 요청 풀어 쓰기에만 "이런 장면에 쓰일 곡" 한 줄을 붙였다.

## 돌아보며

- **평가가 먼저다.** 평가 세트와 캐시를 만든 뒤로는 "좋아진 것 같다"가 아니라 숫자로 되돌릴지 정할 수 있었다. 실제로 세 번 되돌렸다(공감형 풀어 쓰기, 구체 서사형, 9/30 재정렬 순서).
- **모델보다 재료.** 재정렬을 붙였을 때보다 곡 설명의 거짓말("가사 없는 연주곡")을 고쳤을 때 더 많이 움직였다. LLM 이 읽는 글이 엉터리면 LLM 도 엉터리다.
- **임베딩의 고질병은 이름이 있다.** 허브는 평균 빼기로, 글자 그대로 놓치는 건 lexical 가산으로 — 검색 분야에 이미 있는 처방을 가져다 쓰면 됐다.
- **한 규칙이 모든 요청에 맞진 않다.** 위로를 원하는 요청과 공감을 원하는 요청은 다르다. 요청 종류를 나누고, 애매하면 두 갈래로 읽는다.
